Reverse Proxy vs. Load Balancer vs. API Gateway

When designing backend infrastructure and microservices architectures, three components often cause confusion due to their overlapping functionalities: Reverse Proxies, Load Balancers, and API Gateways.

Here is the complete summary extracted directly from the ByteByteGo video deep dive into their technical differences.

1. The Core Problem​

When an application goes viral, a single backend server crashes because it's doing too much at once. It has to handle application logic, database queries, and expensive tasks like SSL encryption, serving static files, and mitigating malicious traffic—all while directly exposed to the public internet.

2. Reverse Proxy (The Protective Shield)​

Unlike a forward proxy (like a VPN) that works on behalf of the client, a Reverse Proxy works on behalf of the server.

  • Purpose: It sits at the edge of your network, receiving requests before they hit your application.
  • Capabilities:
    • SSL Termination: Handles expensive TLS handshakes so the backend server doesn't have to waste CPU cycles.
    • Caching & Compression: Caches identical responses and compresses data (gzip, Brotli) for faster transfers.
    • Security: Hides your backend IP and filters malicious traffic.
  • Examples: NGINX, HAProxy, Caddy, Envoy.
  • Limitation: It is general-purpose and operates mostly at the connection level. It doesn't understand your business logic or API semantics.

3. Load Balancer (Traffic Distribution)​

When a single server maxes out, you add more servers. But how do you decide which server gets which request? A Load Balancer is essentially a reverse proxy that evolved specialized skills for traffic distribution.

  • Purpose: Distributes incoming traffic across a pool of servers to ensure horizontal scalability and high availability.
  • Capabilities:
    • Algorithms: Uses Round Robin, Least Connections, Weights, or IP Hashing to balance traffic based on server capacity.
    • Health Checking: Continuously pings servers. If a server crashes, it immediately routes traffic away from it.
    • L4 vs L7: Layer 4 load balancers handle raw TCP/IP for speed. Layer 7 load balancers understand HTTP and can route based on URLs or headers.
  • Examples: AWS Application/Network Load Balancer.

4. API Gateway (The Intelligent Front Door)​

When moving from monoliths to microservices, every independent service suddenly has to validate tokens, enforce rate limits, and translate request formats. You end up with duplicated infrastructure code maintained by different teams.

  • Purpose: An API Gateway is a specialized reverse proxy that actually understands your APIs.
  • Capabilities:
    • Centralized Authentication & Rate Limiting: Validates JWTs/API keys and throttles traffic centrally so backend services can focus strictly on business logic.
    • Request Transformation: Translates modern JSON requests into legacy XML or routes /v1 to old servers and /v2 to new ones during migrations.
    • Visibility: Provides centralized analytics and monitoring.
  • Examples: Kong, AWS API Gateway, Apigee, Tyk.

5. The "Spectrum" & Real-World Architecture​

The video stresses that these terms confuse people because modern tools blur the lines. For example, NGINX started as a reverse proxy, but acts as a load balancer when you add upstream blocks, and becomes an API gateway when you add OpenResty plugins. Kong is an API Gateway that is actually built on top of NGINX.

In a mature, real-world production system, these tools don't compete; they are layered complementarily:

  1. CDN (Cloudflare/Fastly): A global network of reverse proxies caching static assets at the edge.
  2. API Gateway: Sits at the entry point validating auth and applying rate limits.
  3. Load Balancer: Distributes the approved request across healthy instances of a specific microservice.
  4. Internal Reverse Proxies: Run alongside individual microservices to manage internal service-to-service communication or TLS.
